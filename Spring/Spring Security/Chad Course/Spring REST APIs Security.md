### Authentication Vs Authorization
Authentication and Authorization are key security steps that ensure only the **right users access** a system and can perform permitted actions. ==Authentication verifies who you are, and Authorization determines what you can do.==
- **Authentication**: Confirms the user’s identity.
- **Authorization**: Determines what the verified user is allowed to access or perform.

| **Authentication**                                      | **Authorization**                                                 |
| ------------------------------------------------------- | ----------------------------------------------------------------- |
| Verifies who the user is                                | Determines what the user can access                               |
| Performed before authorization                          | Happens after authentication                                      |
| Requires login details (username, password, biometrics) | Requires user roles, privileges, or access levels                 |
| Determines if the user is valid                         | Determines what permissions the valid user has                    |
| Uses ID Tokens                                          | Uses Access Tokens                                                |
| Governed by OpenID Connect (OIDC)                       | Governed by OAuth 2.0                                             |
| Credentials can be changed by the user                  | Permissions can only be changed by the system owner               |
| Visible to the user (entering credentials)              | Not visible to the user (handled in the background)               |
| Examples: Password, OTP, fingerprint, face recognition  | Examples: Admin rights, read/write access, role-based permissions |

### Configuring Basic Security Declaratively
Using `@Configuration` to configure the spring security module and `@Bean` to generate authorized users who can access the system
##### Example
This configuration class in Spring Security creates an **in-memory authentication system** with 2 users and different roles.

```java
@Configuration
public class DemoSecurityConfig {

    @Bean
    public InMemoryUserDetailsManager userDetailsManager(){

        UserDetails john = User.builder()
                .username("john")
                .password("{noop}test123")
                .roles("EMPLOYEE")
                .build();

        UserDetails susan = User.builder()
                .username("susan")
                .password("{noop}test123")
                .roles("EMPLOYEE", "ADMIN")
                .build();

        return  new InMemoryUserDetailsManager(john, mary, susan);
    }
}
```

* `InMemoryUserDetailsManager` This object acts like a **fake user database stored in memory**. Instead of reading users from MySQL/PostgreSQL, users exist only while the app is running.
* We can define any name for the roles and spring internally store it like `ROLE_XXX`
* Passwords are stored in specific format defined by the encoding identifier in the curly braces

> [!NOTE] Password
> **{encoding Id}thePassword**
> 
> Id Examples:
> * **noop** -> No encoding stored as plain text
> * **bcrypt** -> Stored as hashed password using Bcrypt hashing algorithm

### Restrict Access Based on Roles

After applying these configurations, now we defined all users in the system (*mimic it by the in memory users*) this helps in **Authentication**, but all these users can access any URL.
* So now to apply **Authorization** too we have to restrict access on certain URLs based on **Roles**
##### Using these methods:
```Java
requestMatchers (HttpMethod.PUT, "/api/employees")  -> Http Method + Path Mapping 
.hasRole("MANAGER") -> Single Role

------------------------- OR --------------------------
requestMatchers (HttpMethod.PUT, "/api/employees")  -> Http Method + Path Mapping 
.hasAnyRole("MANAGER", "ADMIN") -> Comma-delimited list of Roles
```

##### Example 
```Java
@Bean  
public SecurityFilterChain filterChain(HttpSecurity http) throws Exception{  
	http.authorizeHttpRequests(configurer -> configurer  
		.requestMatchers(HttpMethod.GET, "/employees").hasRole("EMPLOYEE")                 .requestMatchers(HttpMethod.GET, "/employees/**").hasRole("EMPLOYEE")  
		.requestMatchers(HttpMethod.POST, "/employees").hasRole("MANAGER")  
		.requestMatchers(HttpMethod.PUT, "/employees/**").hasRole("MANAGER")  
		.requestMatchers(HttpMethod.PATCH, "/employees/**").hasRole("MANAGER")             .requestMatchers(HttpMethod.DELETE, "/employees/**").hasRole("ADMIN")  
	);  

	// use HTTP Basic authentication  
	http.httpBasic(Customizer.withDefaults());  

	// disable Cross Site Request Forgery (CSRF)  
	http.csrf(AbstractHttpConfigurer::disable);  

	return http.build();  
}  
```

==Now, we restrict access on specific URLs based on user role==

> [!NOTE] Notes
> `httpBasic()` -> It enables authentication using
> * Authorization: **Basic username:password**
> 
> This is why **Postman/browser** can authenticate using (username, password)
> Another common authentication method rather than the basic one is **JWT** 
> 
> `http.csrf(AbstractHttpConfigurer::disable)` **usually disabled for REST APIs** because its stateless **and** don't rely on sessions so no need for protection against **CSRF attack** 

> For more details about CSRF review this page **[[Cross-Site Request Forgery (CSRF)]]**

### Add Database Support

For the previous configuration users are stored in-memory just for testing, now we want to store these users in **DB**. Spring security uses **JDBC** to query users' information

* Spring expects that in our schema we have **2 tables** `users` and `authorities` 

![[Pasted image 20260516002225.png|434]]

```sql
INSERT INTO `users`
VALUES
('john','{noop}test123',1),
('susan','{noop}test123',1);

INSERT INTO `authorities`
VALUES
('john','ROLE_EMPLOYEE'),
('susan','ROLE_EMPLOYEE'),
('susan','ROLE_MANAGER'),
('susan','ROLE_ADMIN');
```

Now spring can **automatically** access these tables with each login for **authentication**
##### New Configuration
```java
@Bean  
public UserDetailsManager userDetailsManager(DataSource dataSource){  
    return new JdbcUserDetailsManager(dataSource);  
}
```

> `UserDetailsManager` is an **interface** which implemented by `JdbcUserDetailsManager` and `InMemoryUserDetailsManager`


> [!NOTE] For Bcrypt Password
> **Example** -> {bcrypt)$2a10qeS0HEh7urweMojsnwNAR.vcXJeXR1UcMRZ2WcGQI9YeuspUdgF
> 
>**Spring Security Filter Process:**
>* Retrieve password from DB for the user 
>* Read the encoding algorithm id (bcrypt etc.) 
>* For case of bcrypt, encrypt plaintext password from login form (using salt from DB password)
>* Compare encrypted password from login form with encrypted password from DB 
>* If there is a match, login successful, If no match, login failed
>
>The passwords from DB are **never decrypted** because Bcrypt is a **one-way** hashing algorithm

### Custom Table Schema

We don't have to follow spring security schema, we can use a custom tables if we want to use our own schema 


> [!NOTE] For this customization
> **Tell Spring how to query your custom tables**
> * Provide query to find user by user name
> * Provide query to find authorities / roles by user name

##### Example
```Java
@Bean  
public UserDetailsManager userDetailsManager(DataSource dataSource){  
    JdbcUserDetailsManager userDetailsManager = new 
                           JdbcUserDetailsManager(dataSource);  
  
    userDetailsManager.setUsersByUsernameQuery(
	    "select user_name, pw, active from members where user_name=?"
    ); 
     
    userDetailsManager.setAuthoritiesByUsernameQuery(
	    "select user_name, role from roles where user_name=?"
    );  
  
    return userDetailsManager;  
}
```

> The parameter **user_name=?** this value will be passed by the **login form**
